# R2 media storage

The backend supports one private R2 bucket for images and videos. Accounts, wallets,
templates, and storage references remain in the database. Neon PostgreSQL is selected when DATABASE_URL is set; SQLite remains available
for offline development. See NEON.md for setup and existing-data migration.

## Configuration

Set the following in backend/.env or deployment secrets. Never put them in the
frontend, Expo public variables, source control, or dashboard content:

```dotenv
R2_ACCOUNT_ID=your-account-id
R2_ENDPOINT=https://your-account-id.r2.cloudflarestorage.com
R2_ACCESS_KEY_ID=your-access-key-id
R2_SECRET_ACCESS_KEY=your-secret-access-key
R2_BUCKET=ai-creator-media
R2_REGION=auto
```

Use the jurisdiction-specific endpoint from Cloudflare if applicable. The API token
needs Object Read & Write access scoped to this bucket. Keep Public Development URL
and public custom-domain access disabled.

R2 is selected automatically when R2_BUCKET is set. Incomplete R2 configuration
fails startup instead of silently storing files locally. With no bucket configured,
local development continues to use data/uploads. MEDIA_STORAGE=local explicitly
selects local storage; it cannot read objects already moved into R2.

Existing files on disk remain readable when R2 is enabled. The backend tracks which
uploads live in R2 and which are local. Startup creates the configured database schema; local SQLite upgrades are additive.
Moving existing SQLite records into Neon uses the separate database:migrate command.

## File handling

- Input uploads and admin artwork accept PNG, JPEG, and WebP up to 10 MB, with
  file-signature checks and an enforced per-user input upload quota of 200 MB.
- AI image results accept PNG, JPEG, and WebP; video/dance/slideshow results accept
  MP4. Provider output downloads are capped at 256 MB and use temporary disk files.
- Uploaded photos use uploads/images/<user>/<file>; artwork uses templates/<file>;
  generated outputs use generated/images/<user>/<job> or generated/videos/<user>/<job>.
- Private upload downloads require the existing user session and ownership check.
- Template artwork marked public in the application is served by the backend's
  existing /media route. The bucket itself remains private.
- A successful R2-backed job stores a permanent object reference, not an expiring
  provider link. Job API responses issue signed GET URLs after checking ownership
  (administrators can also view jobs). Links last approximately 55–60 minutes.
- Storage retries reuse the completed provider result instead of generating again.
  A job receives completion rewards only after its output is stored. Repeated
  storage failure follows the existing retry/refund policy.
- The app obtains a fresh result link before saving/sharing and uses the actual
  media type and extension. Signed URLs are bearer access links: anyone possessing
  one can use it until expiry; they are not permanent public links.
- Account deletion removes uploaded inputs and stored generated outputs. Failed
  storage deletion leaves the account retryable. The cleanup command removes old
  private inputs from their actual storage location and preserves active job inputs.

The server checks HTTPS, public DNS addresses, redirects, media signatures, and
file sizes before copying provider output. No provider credentials are forwarded
to output hosts. R2 SDK errors are replaced with generic API messages.

## Verify the connection

To copy existing uploads, available generated results, and the five bundled sample
images, stop the backend and run `npm run storage:migrate -- --results --bundled`.
Bundled images are downloaded back and compared byte-for-byte before their R2
references are saved in the database. The dashboard's `/seed-assets` routes then
serve those images from R2. Local originals and mobile offline artwork are retained.
The command can be repeated without duplicating completed records.

From backend/, after entering real credentials:

```sh
npm run storage:check
```

This explicit live check uploads a tiny PNG, downloads it, verifies its bytes, and
deletes it. It prints only success/failure, never secrets or signed URLs. It does
not run automatically at startup. Automated tests use simulated storage and do
not load .env or contact R2.

## Browser access

App uploads and template images go through the backend; they need no direct-upload
CORS rule on the bucket. If the web preview requests private signed media directly,
set the bucket CORS policy to allow GET and HEAD from the actual web app origins:

```json
[
  {
    "AllowedOrigins": ["http://localhost:8081", "https://your-web-app.example"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["Range"],
    "ExposeHeaders": [
      "Content-Length",
      "Content-Range",
      "Accept-Ranges",
      "ETag"
    ],
    "MaxAgeSeconds": 3600
  }
]
```

Replace the example production origin with your domain. CORS does not make the
bucket public. Native Android access does not rely on browser CORS rules.

## Move existing media

Back up the database first. Finish/cancel pending jobs and stop the backend so that
media references cannot change during the migration. Then, from backend/:

```sh
npm run storage:migrate
```

This copies local uploads to R2 and updates their database references. It keeps
original local files for rollback, skips completed records, and can be resumed.
After verifying the migration and your backup, you can remove retained local copies.
Account deletion/cleanup also remove retained local upload copies.

To also copy existing successful provider outputs that are still downloadable:

```sh
npm run storage:migrate -- --results
```

Expired provider URLs cannot be recovered by this migration. Run cleanup during a
maintenance window with incoming submissions paused, since it is a separate process.
Keep backend/data/master.key with your protected database backups; R2 credentials
and the existing provider encryption key serve different purposes.

The npm run backup command backs up the configured database (pg_dump for PostgreSQL),
local files, and the encryption key. It does not make a second copy of R2 objects. Maintain a separate R2 backup
policy and restore the database and media from a matching snapshot. Do not add a
blanket lifecycle deletion rule that would erase generated results or template art.
