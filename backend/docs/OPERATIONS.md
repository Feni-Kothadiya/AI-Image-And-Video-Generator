# Running and maintaining Creator Studio

## Database selection

DATABASE_URL selects Neon PostgreSQL; an unset URL selects local SQLite.
See [Neon setup and migration](NEON.md) before starting against a fresh Neon database
if you want to retain local accounts. R2 handles images/videos independently.

## Local setup

Use Node 22.13 or later (the workspace .nvmrc selects Node 22). From backend:

    npm ci
    npm --prefix ../frontend ci
    npm --prefix ../frontend run build
    npm run setup
    npm start

Setup creates a random admin password once; it never overwrites an existing administrator.
Credentials are saved locally under data/admin-credentials.txt with restrictive file mode
where supported. Change the password in the dashboard and remove or secure that initial file.
On Windows, ensure the data folder's NTFS permissions allow only the server owner/service account.

Optional initial setup environment: ADMIN_EMAIL, ADMIN_PASSWORD (12+ characters), DATA_DIR.
Do not commit those values. There is no shared/default admin password.

The backend serves the sibling frontend/dist compiled dashboard at http://localhost:4000.
Its default bind address is 127.0.0.1. The mobile USB script forwards port 4000 to the phone.
If running Vite separately, set ADMIN_ORIGIN=http://localhost:5173 for that development session;
Vite proxies API/media requests to port 4000. Restore port 4000 when serving the compiled dashboard.

The default content and public seed artwork live in the sibling shared/ directory.
Keep that directory alongside backend/ when deploying. The default dashboard build
is ../frontend/dist; FRONTEND_DIST can point to another compiled frontend directory.
The API can also run without a dashboard build.

## Content publishing

For fal.ai image/video generation, set FAL_KEY and run `npm run fal:setup` before
starting the backend. See [FAL.md](FAL.md) for models, spending estimates, signed
input/output links, and the explicit paid smoke test. Generation can be paused
from the dashboard Integrations page. The provider does not support slideshows.

Editors save drafts and publish explicitly. Prices/costs are captured when a job is accepted,
so a later publication does not change a queued job's charge or promised completion reward.
Restore operations preserve published history and update only the draft.

New application source can introduce new copy. From the app root:

    node scripts/seed-content.cjs

Then from backend, while the backend is running:

    npm run sync:texts

This adds missing text lookup keys to the draft without replacing customized values.
It uses the initial local admin credentials, so use the dashboard after changing that password.
Review and publish the draft. Existing native code continues using bundled fallback strings
until the app receives published overrides.

## Data

For private image/video storage in Cloudflare R2, see [R2 setup](R2.md).
R2_BUCKET enables remote media storage; DATABASE_URL independently selects PostgreSQL.
The backup command covers the configured database and local files, not R2 object copies.

| Path                       | Purpose                                                             |
| -------------------------- | ------------------------------------------------------------------- |
| data/studio.sqlite         | Accounts, sessions, ledger, drafts, revisions, jobs, reports, audit |
| data/uploads/              | Private input photos and public template artwork                    |
| data/master.key            | AES-GCM encryption key for provider secrets; never lose or publish  |
| data/admin-credentials.txt | Initial local administrator credentials                             |
| data/backups/              | Local backups generated by the backup command                       |

SQLite migrations are in server/migration.sql and server/db.mjs; PostgreSQL tables
are defined in server/postgres.sql. Parameterized queries are used for
data access. Backups must include the database, uploaded files, and master.key.

    npm run backup

For Neon, install a compatible pg_dump and set DIRECT_DATABASE_URL; the command
creates a postgres.dump archive. Restore it with pg_restore into an appropriate
empty PostgreSQL database. Keep the matching master.key and media backup.

When using SQLite, the SQLite backup API makes a consistent database copy. Pause incoming uploads/deletions while
backing up if you need database and media to form an exact snapshot. Keep an encrypted off-machine
copy; a backup only on the same disk does not protect against losing the PC.

To restore, stop the server, preserve the current data directory, and replace studio.sqlite,
uploads/, and master.key together from a matching backup. Do not copy stale -wal/-shm files
from a different database. Test restoration on a separate instance before replacing live data.

    npm run cleanup

Cleanup removes private input photos older than 72 hours unless referenced by an unfinished job.
It leaves public media and output URLs alone, and removes expired sessions.
Schedule it daily in production. Account deletion also removes the user's private input files.

## Production deployment

This project is ready for local review; it has not been publicly deployed.

For Render, follow [the Render guide](RENDER.md) and the root `render.yaml` instead
of the manual reverse-proxy configuration below. Render binds to `0.0.0.0` and
supplies the port and TLS endpoint.

1. Use a persistent-disk Node server with one process and a service account.
2. Install backend dependencies with npm ci, then build the sibling frontend with
   npm --prefix ../frontend ci and npm --prefix ../frontend run build.
3. Keep data/ outside the web root; only explicit public media routes serve files.
4. Configure NODE_ENV=production, ADMIN_ORIGIN=https://your-domain, HOST=127.0.0.1,
   PORT=4000, and an appropriate DATA_DIR.
5. Put an HTTPS reverse proxy in front. Set TRUST_PROXY=1 only when that proxy overwrites
   forwarding headers and direct access to the backend is blocked.
6. Restrict admin network access as appropriate for your team. The built-in system currently
   has one administrator role; granular staff roles and MFA are not implemented.
7. Configure monitoring for /api/health, disk space, job failures, and process restarts.
8. Schedule backups and cleanup; test a restore.
9. Set EXPO_PUBLIC_API_URL to the HTTPS API domain and rebuild the Android app.
10. Test final media permissions in a native Android development/release build.

Before public paid use, connect and test the chosen AI vendor, durable output storage,
Google Play purchase verification/entitlements, ad reward verification, email verification/recovery,
and final legal content. Those services cannot be validated with credentials that have not been provided.

## Security boundaries

- Admin cookies are HttpOnly, SameSite Strict, and Secure in production.
- Admin mutations require an explicit configured Origin plus a per-session CSRF token.
- Passwords use scrypt with per-password random salts. Sessions store token hashes.
- API keys are encrypted at rest; the app sees availability flags, never secrets.
- Native tokens use Expo SecureStore. Browser preview uses local storage only for local QA.
- Coins are changed only by server transactions, not client-supplied balances.
- Private uploads require ownership checks. Public uploads are PNG/JPEG/WebP with size/signature checks.
- No production mock generation, purchase grant, or unverified ad-credit endpoint is enabled.
- Gateway host restrictions, HTTPS, public DNS checks, and address pinning limit outbound destinations.
- Server-side rate limiting is in memory and resets on restart; use a shared limiter before scaling.
- Guest creation is limited per IP, but it does not provide device attestation or prevent determined
  account farming. Add Play Integrity/account verification before offering valuable free credits publicly.
